Tiny Infer

A transformer inference engine in plain C, built to run a 15M-parameter TinyStories-format model on a CPU, one token at a time, with no PyTorch and no BLAS.

Result
121 tokens/s on 1 thread, 188 on 2, with about 91% of the time in matmul. Measured on a 2-vCPU cloud VM with synthetic weights. No numbers on real weights yet.

Why build it

I use models all day in research, but PyTorch hides the part I wanted to understand: the work the CPU does to produce the next word. In C, I write every matmul and manage every buffer and thread myself.

It's also a test bed for an idea from my research. A Mixture-of-Experts model only uses a few experts per token. If you can guess which ones come next, you can load their weights early and keep the CPU busy. The last item on the roadmap is a toy MoE layer to try that.

One token, start to finish

  1. Look up the token's embedding.
  2. For each layer: RMSNorm, then three matmuls for the query, key, and value vectors.
  3. Rotate the query and key by the token's position (RoPE), and write the key and value into the KV cache so later tokens don't recompute them.
  4. Score the query against every cached key, softmax the scores, and mix the cached values.
  5. Project back, add the residual, then RMSNorm and the SwiGLU feed-forward, and add the residual again.
  6. After the last layer, one more matmul turns the hidden state into a score for every word in the vocabulary, and the sampler picks one (greedy, or with temperature).

I mmap the model file, so startup is close to instant and the OS pages weights in as they're used. Prompts go through a BPE encoder I wrote against the llama2.c tokenizer format.

Where the time goes

make bench builds a separate -O3 -march=native -ffast-math binary (so I can't time a debug build by accident), generates 200 tokens with greedy sampling, throws away a warm-up run, and reports the median of 5. The tokenizer and printing stay off the clock. It splits each token's time into matmul, attention, sampling, and everything else.

The first measurement ran at 666 tokens per second with 96.5% of the time inside matmul(), but that skeleton only had the embedding and the output layer, so it mostly confirmed the timers work.

Both runs used a 2-vCPU cloud VM (Intel Xeon, 2.8 GHz) and synthetic weights shaped like stories15M. The weight values don't affect speed, but these aren't laptop numbers or the real model. Results with the full forward pass:

Making matmul faster

Threads

A pthreads pool splits the output rows of each matmul across cores. Rows are independent, so threads never write to the same memory. -j sets the thread count. By default it uses every core.

int8 weights

--int8 stores every weight as an 8-bit integer in groups of 32, with one float scale per group (scale = max|w| / 127). Activations get the same treatment just before each matmul, so the inner loop multiplies int8 by int8 and adds up in int32. That's about a quarter of the memory traffic of fp32. --compare runs both versions on the same prompt and prints the numeric error, the speed of each, and both stories side by side, so I can see when quantization changes the output.

Testing and CI

Every kernel (matmul, softmax, RMSNorm, the thread pool, int8) has its own self-test, run by make test. make debug rebuilds with the address and undefined-behavior sanitizers on.

Two real bugs so far. The loader checks that the weights end exactly where the file does, and that check showed I was skipping twice too many floats for llama2.c's unused legacy RoPE tables, so real checkpoints would have been rejected. And the macOS build broke because macOS hides the constant I use to count cores (_SC_NPROCESSORS_ONLN) when only _POSIX_C_SOURCE is set. Defining _DARWIN_C_SOURCE fixed it.

One GitHub Actions workflow chains four jobs: build-and-test → sanitizers → package → release. Pushes and pull requests run the first two on Linux and macOS. A version tag runs all four jobs and attaches Linux and macOS binaries to a GitHub release, though I haven't tagged one yet.
